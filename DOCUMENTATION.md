# Vault — Mobile Banking App

> A modern fintech-style mobile banking app built with Flutter & Firebase for a
> 3-person university software project. This document explains **what the app
> does, how it is built, why each decision was made, and who was responsible for
> what** — everything needed to understand and present the project.

---

## 1. At a glance

**Vault** is a simulated mobile bank. A user can create an account, sign in,
see their balance (with a privacy toggle), deposit money, send money to other
users, set savings goals, view spending insights, and play a short financial-
literacy quiz.

| | |
|---|---|
| **Platform** | Flutter (Android-first; iOS-ready code) |
| **Language** | Dart 3.11 |
| **State management** | Riverpod |
| **Navigation** | GoRouter (auth-gated) |
| **Backend** | Firebase Authentication + Cloud Firestore |
| **Charts** | fl_chart |
| **Local prefs** | shared_preferences |
| **Currency** | XAF (Central African CFA franc) |
| **Design** | Material 3, customised into a dark fintech theme |

---

## 2. Visual & design direction

The UI is a **dark-mode-first fintech** look (inspired by Revolut / Monzo / Cash
App):

- Near-black background (`#0A0A0F`), dark surfaces (`#1A1A24`).
- A single vibrant brand accent — electric purple `#7C3AED`.
- A purple→pink **atmospheric gradient bloom** used *only* behind hero areas
  (the balance card, auth/onboarding) — never on buttons, which use flat fills.
  This restraint is deliberate: gradients on controls are the hallmark of
  template UI, while a soft background bloom reads as premium.
- **Mixed-size metrics**: the balance number is large (56px), the currency code
  small — the eye lands on the amount.
- **Glassmorphism**: the balance card is a real frosted-glass card (backdrop
  blur + translucent fill + hairline edge + soft shadow).
- **Purposeful motion**: every tap has fast (120 ms) feedback; rare, meaningful
  moments (deposit/transfer success, quiz score) get a slightly playful
  overshoot animation. All motion respects the OS "reduce motion" setting.

Everything is driven by a small **design-system token layer** (colours,
spacing, radii, durations, shadows, text styles) so there are no "magic numbers"
and the look stays consistent.

## 3. Tech stack & why

| Choice | Why |
|---|---|
| **Flutter** | One codebase, native performance, excellent for a polished custom UI. |
| **Firebase Auth** | Secure, managed email/password auth + password reset out of the box — no need to build/secure our own auth server. |
| **Cloud Firestore** | Real-time database: balances and transaction lists update live on screen via streams. |
| **Riverpod** | Compile-safe, testable state management; providers expose Firebase streams to the UI cleanly. |
| **GoRouter** | Declarative routing with a single redirect rule that gates the whole app behind authentication. |
| **fl_chart** | Lightweight, customisable charts for the spending-insights feature. |
| **shared_preferences** | Tiny on-device store for non-sensitive UI prefs (onboarding seen, hide-balance default). |

## 4. Architecture

```
lib/
├── main.dart                  # App entry: Firebase init, ProviderScope, MaterialApp.router
├── firebase_options.dart      # Generated by FlutterFire (gitignored — contains keys)
├── app/
│   ├── routes.dart            # All route path constants
│   └── router.dart            # GoRouter + auth redirect logic
├── features/                  # One folder per feature (screens + feature widgets)
│   ├── auth/                  # sign in / sign up / forgot password
│   ├── onboarding/            # first-run swipeable intro
│   ├── dashboard/             # home: balance, quick actions, recent activity
│   ├── deposit/               # add money
│   ├── transactions/          # full filterable history
│   ├── transfer/              # peer-to-peer send (innovation)
│   ├── goals/                 # savings goals / pots (innovation)
│   ├── insights/              # spending charts (innovation)
│   ├── card/                  # virtual card (innovation)
│   ├── loan/                  # loans with credit scoring (innovation)
│   ├── quiz/                  # financial-literacy game
│   └── settings/              # profile, prefs, sign out
└── shared/                    # cross-feature building blocks
    ├── theme/                 # AppColors, AppTextStyles, AppSpacing/Radii/Durations/Shadows, AppTheme
    ├── widgets/               # PrimaryButton, GlassCard, BalanceText, GradientBloom, AppTextField, EmptyState…
    ├── models/                # UserProfile, BankTransaction, QuizQuestion, SavingsGoal, VirtualCard, Loan
    ├── services/              # FirebaseAuthService, FirestoreService, PrefsService (+ Riverpod providers)
    ├── utils/                 # currency formatting, validators
    └── strings.dart           # all user-facing copy in one place
```

### Layered design
- **UI (features/)** never talks to Firebase directly. It watches **Riverpod
  providers**, which wrap the **services**, which wrap Firebase. This keeps
  screens simple and the data logic testable in one place.
- **All money mutations are atomic.** Deposits, transfers and goal moves run
  inside Firestore **transactions**, so a balance and its ledger entry can never
  drift apart, even with concurrent writes.

### Data model (Firestore)
```
users/{uid}                     → { email, displayName, balance, createdAt }
users/{uid}/transactions/{id}   → { amount, type, description, balanceAfter, createdAt }
users/{uid}/goals/{id}          → { name, target, saved, createdAt }
users/{uid}/cards/{id}          → { number, holder, expMonth, expYear, cvv, frozen, createdAt }
users/{uid}/loans/{id}          → { principal, termMonths, ratePct, totalRepayable, outstanding, monthlyPayment, purpose, status, createdAt }
quiz_questions/{id}             → { question, choices[], correctIndex, funFact }
```

### Security rules (`firestore.rules`)
- A user can read/write **their own** profile, transactions, goals, cards and loans.
- Profiles are **readable by any signed-in user** so a transfer can look up a
  recipient by email.
- `quiz_questions` are read-only to clients (seeded by an admin script).
- **Transfer note:** crediting another user's balance from the client requires
  a relaxed write rule. In a production app this cross-user write belongs in a
  **Cloud Function** (server-enforced "debit == credit"). Cloud Functions need
  Firebase's paid Blaze plan, so for this project the transfer runs client-side
  in an atomic transaction with a documented relaxed rule. This is a deliberate,
  understood trade-off.

### Routing & auth gate
`router.dart` listens to the Firebase auth stream. One `redirect` rule decides:
- not onboarded → **Onboarding**
- onboarded but signed out → **Sign in**
- signed in → **Dashboard** (and signed-in users can't go back to auth screens).

## 5. Features — what each does & why

### Required by the brief

**1. Sign up / Sign in / Sign out** *(auth)*
Email + password via Firebase Auth, with inline validation and friendly error
messages (e.g. wrong credentials collapse to one "Email or password is
incorrect" message — good security practice, doesn't reveal whether an email is
registered). On sign-up the app also creates the user's Firestore profile.
*Why:* core requirement; Firebase gives secure, reliable auth without a custom
server.

**2. Good UI**
Covered by the design system in section 2 — consistent dark fintech theme, glass
balance card, atmospheric bloom, purposeful motion, empty/loading/error states
everywhere.
*Why:* the brief explicitly rewards polish; a coherent design system makes every
screen feel intentional.

**3. Balance with hide/show toggle** *(dashboard)*
The balance streams live from Firestore and is shown as a large mixed-size
metric. An eye icon toggles it to `••••••`; the preference persists and can be
defaulted to "hidden" in Settings.
*Why:* a standard banking privacy feature; the persisted default shows attention
to real user needs.

**4. Firebase auth + password recovery** *(auth)*
"Forgot password?" sends a Firebase reset email.
*Why:* required; offloads the sensitive reset flow to Firebase.

**5. Simulated deposit** *(deposit)*
A validated amount form (with quick-amount chips) credits the balance through an
atomic transaction and writes a ledger entry, then shows an animated success
checkmark.
*Why:* required "simulated deposit"; the atomic write keeps data consistent and
the animation makes the action feel rewarding.

**6. Financial-literacy quiz** *(quiz)*
Pulls 15 seeded questions, picks 5 at random per game, gives instant correct/
wrong feedback, shows a **fun-fact dialog** per question, and ends on an animated
score reveal with "play again".
*Why:* required "quiz with fun facts"; randomisation + fun facts make it
replayable and genuinely educational about banking safety.

### Innovations (added to impress)

**7. Peer-to-peer transfers** *(transfer)*
Send money to another Vault user by email. The recipient is looked up by email,
then a single Firestore transaction debits the sender, credits the recipient,
and writes a ledger entry for **both** sides (a withdrawal for the sender, a
deposit for the recipient).
*Why:* the most "real bank" feature and the strongest engineering story —
demonstrates atomic cross-document transactions and an understanding of where
server-side logic (Cloud Functions) would belong in production.

**8. Spending insights** *(insights)*
A balance-over-time line chart plus total-in / total-out / net / movement-count
tiles, all computed from the existing transaction ledger (no extra data stored).
*Why:* turns raw transactions into something meaningful and visual; great demo
payoff and shows data-derivation skills.

**9. Savings goals ("pots")** *(goals)*
Create goals with a target, move money in/out (debited from / refunded to the
main balance atomically), and watch an animated progress ring fill. Deleting a
goal refunds its balance.
*Why:* an engaging, visual money-management feature; reinforces the atomic-money
pattern and adds personality (Monzo-style pots).

**10. Virtual card** *(card)*
Issue a (simulated) virtual card — a Luhn-valid number, CVV and expiry — shown as
a gradient card you tap to flip and reveal its details. Freeze/unfreeze it, and
make simulated **online payments** that debit the balance and log a `Card •
merchant` transaction.
*Why:* virtual cards are how modern banks let users pay online safely without
exposing their real card; freezing instantly is a flagship neobank feature.

**11. Loans** *(loan)*
Apply for a loan with a **live eligibility preview**: the app computes a credit
score from your income + account activity, shows the max you qualify for, the
rate, and the monthly repayment, then (if approved) disburses to your balance and
tracks repayment with a progress bar.
*Why:* credit is core to banking; basing eligibility partly on real in-app
behaviour mirrors how modern lenders use transaction data for instant decisions.

**Supporting:** Onboarding (first-run intro, shown once), Transactions (full
history with All/Deposits/Withdrawals filter), Settings (profile, hide-balance
default, confirmed sign-out).

## 5a. Innovations — and why they matter in modern banking

The app goes beyond the brief with five innovations. Each is something real
banks/neobanks (Revolut, Monzo, Cash App) actually offer, and each demonstrates a
distinct engineering or design skill.

| Innovation | What it does | Why it matters in modern banking |
|---|---|---|
| **Peer-to-peer transfers** | Send money to another user by email; one atomic Firestore transaction debits the sender, credits the recipient, and records both ledger entries. | Instant P2P payments (think Cash App / Revolut) are now an expectation, not a luxury. The atomic transaction guarantees money is never created or lost — the core correctness property of any payment system. |
| **Spending insights** | Balance-over-time chart + total in/out/net/movements, derived purely from the transaction ledger. | Personal-finance analytics drive engagement and help users budget; deriving insight from raw transactions is exactly what modern banking apps do to add value on top of plain statements. |
| **Savings goals (pots)** | Ring-tracked goals you fund from your balance and can withdraw/delete, all atomic. | "Pots/spaces/vaults" are a signature neobank feature that nudges healthier saving behaviour and increases stickiness. |
| **Virtual card** | Simulated Luhn-valid card with flip-to-reveal, freeze/unfreeze, and online payments that hit the ledger. | Virtual cards let people pay online without exposing their real card, and instant freeze is a key fraud-control users love — a hallmark of digital-first banks. |
| **Loans** | Credit-scored loan application with a live eligibility preview, disbursement to balance, and repayment tracking. | Data-driven, instant lending decisions (using account behaviour, not just paperwork) are how modern fintech lenders operate — fast, transparent, and accessible. |

**Cross-cutting engineering themes the innovations showcase:**
- **Atomic money movement** — every balance change (deposit, transfer, card
  payment, goal move, loan disburse/repay) runs in a Firestore transaction, so
  data can never drift.
- **Real-time UI** — balances, lists, goals, cards and loans all update live via
  streamed providers.
- **Derived intelligence** — insights and loan credit-scoring are computed from
  existing data rather than stored, showing data-modelling maturity.
- **Honest production awareness** — the transfer's relaxed rule is documented with
  the note that production would use a Cloud Function.

### How the spending-insights graph is built

The analytics chart is rendered with the **`fl_chart`** package (added in
`pubspec.yaml`). The implementation lives in
`lib/features/insights/insights_screen.dart`:

1. **Data source** — it watches `transactionsStreamProvider(uid)` to get the live
   ledger (newest-first). No analytics data is stored separately; the chart is
   derived on the fly.
2. **Turning transactions into points** — the list is reversed to oldest-first,
   then mapped to chart points: for each transaction `i`, a
   `FlSpot(i.toDouble(), transaction.balanceAfter)` is created. So the x-axis is
   the transaction sequence and the y-axis is the running balance after each one.
3. **Drawing it** — the points are passed to the **`LineChart`** widget via a
   **`LineChartBarData`** inside **`LineChartData`**:
   - `LineChart(LineChartData(lineBarsData: [LineChartBarData(spots: spots, …)]))`
   - `isCurved: true` smooths the line; `belowBarData: BarAreaData(gradient: …)`
     paints the soft purple fade under it; grid/titles/border are hidden for a
     clean, minimal look.
4. **The summary tiles** (Total in / Total out / Net / Movements) are plain Dart:
   the transaction list is folded — deposits summed into `totalIn`, withdrawals
   into `totalOut`, with `net = totalIn − totalOut` and `movements = list length`.

In short: **`fl_chart`'s `LineChart` / `LineChartBarData`, fed a `List<FlSpot>`
built from each transaction's `balanceAfter`.**

## 6. Team responsibilities — assigned vs delivered

The project was split into three developer areas. Below is what each developer
was **assigned** and what was **delivered** in that area.

### Dev A — Authentication + Firebase setup
**Assigned:** `lib/features/auth/` and the Firebase service layer.
**Delivered:**
- Firebase project setup (Auth + Firestore + security rules + FlutterFire config).
- `FirebaseAuthService` — sign up, sign in, sign out, password reset, auth-state
  stream, friendly error mapping.
- `FirestoreService` — profile creation, balance/transaction/goal streams, and
  all atomic money operations (deposit, transfer, goal moves).
- Auth screens: **Sign in**, **Sign up** (creates the profile), **Forgot
  password**, with validation and a shared auth layout.
- Fixed a real bug found during testing: the profile doc wasn't being written
  because the sign-up screen was disposed mid-write by the router redirect —
  resolved by capturing services before the `await` and self-healing on sign-in.

### Dev B — Banking core (dashboard, deposit, transactions)
**Assigned:** `lib/features/dashboard/`, `lib/features/deposit/`,
`lib/features/transactions/`.
**Delivered:**
- **Dashboard** — greeting, live glass **balance card** with hide/show toggle and
  the atmospheric bloom, a quick-actions grid, and a recent-activity preview.
- **Deposit** — validated amount entry with quick-amount chips and an animated
  success state.
- **Transactions** — full history with a segmented All / Deposits / Withdrawals
  filter and a reusable transaction tile (also used on the dashboard).

### Dev C — Engagement (quiz, settings, onboarding)
**Assigned:** `lib/features/quiz/`, `lib/features/settings/`,
`lib/features/onboarding/`.
**Delivered:**
- **Quiz** — question/answer flow with instant feedback, per-question fun-fact
  dialog, and an animated score reveal; questions seeded into Firestore.
- **Settings** — account summary, "hide balance by default" preference, and a
  confirmed sign-out.
- **Onboarding** — a swipeable three-slide intro with an animated page
  indicator, shown only on first launch.

### Shared work & innovations
The `lib/shared/` design system (theme, reusable widgets, models, utilities) and
the GoRouter navigation layer were built as shared foundations that all three
areas build on. The five **innovations** — peer-to-peer transfers, spending
insights, savings goals, the virtual card, and loans — extend the same shared
service + design layers (each adds a model, `FirestoreService` methods with
atomic transactions, and a feature screen) and were delivered as joint
enhancements on top of the core areas above.

## 7. How to run it

> One developer (Dev A) does the Firebase setup once and shares the config; see
> `docs/FIREBASE_SETUP.md` for the full walkthrough.

1. **Install deps:** `flutter pub get`
2. **Firebase config:** `flutterfire configure --project=dart-project-bank`
   (generates `lib/firebase_options.dart`, which is gitignored).
3. **Enable** Email/Password auth and create the Firestore database in the
   Firebase console; deploy rules with `firebase deploy --only firestore:rules`.
4. **Seed the quiz:** `cd scripts && npm install && node seed-quiz.js`
   (needs `scripts/service-account.json` from the console — gitignored).
5. **Run:** `flutter run` (use `flutter run --release` for the smoothest demo on
   an emulator).

## 9. Security & production notes

- Secrets (`google-services.json`, `GoogleService-Info.plist`,
  `firebase_options.dart`, service-account keys) are **gitignored** and never
  committed.
- All balances change only through **atomic Firestore transactions**.
- **Known trade-off:** peer-to-peer transfers run client-side with a relaxed
  Firestore write rule because Cloud Functions require the paid Blaze plan. In
  production the transfer (and any cross-user write) would move into a Cloud
  Function so the server enforces correctness. This is intentional and
  documented in `firestore.rules`.
